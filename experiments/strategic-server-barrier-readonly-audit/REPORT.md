# Independent native barrier review

The installed server barrier has no identified blocker for the registered turn-start, no-active-battle acceptance protocol. This is source review, not a claim of runtime correctness. SOURCE_REVIEW.json contains exact native source SHA and numbered excerpts; FAILURE04.json preserves the previous failing terminal sequence.

In acceptance04, the last real fight completes, the server sends BattleEnded (23965), then PlayerEndsGame (23981/23990). The client processes BattleEnded and immediately issues MoveHero request310 (24002–24004), before consuming PlayerEndsGame (24010 onwards). There is no server receipt or actual execution proof for this extra request: 195 decisions versus 194 confirmed moves. This is a spurious action, not an executed terminal action with a missing ACK. No-query termination bypassed the previous query-ACK gate.

The new design keeps battleBusy until an explicit server END. engageIntoBattle records only valid players. CGameHandler checks readiness after the entire incoming request apply and its PackageApplied: both own query stack empty and no current battle involving that player. BattleResultProcessor keeps currentBattles through all players' battle-query removals; it emits BattleEnded before checkVictoryLossConditions. Moving readiness to the outer request tail therefore waits past both orderings seen in failures03 and04 and past that request's recursive visit, level-up and victory processing. Opponent MakeAction ACK cannot be used as the sole Director wakeup: client dispatches PackageApplied only to pack.player.

Director's ordinary movement/query/economy/pending request gates remain active at END. A PlayerEndsGame emitted by the same apply precedes END on the connection and clears turnActive. Nullkiller2's playerBlocked only handles UPCOMING_BATTLE START and ONGOING_MOVEMENT, so the added END does not alter its scheduling code.

Limits retained: pendingBattleBarriers is transport state and is not serialized, so this review does not certify active-battle saves/reconnects. Any battle completion outside incoming-request processing would need an explicit outer dispatch drain; the present fixtures complete through MakeAction/QueryReply. The existing native handler sends PackageApplied(true) even when the visitor result is false (CGameHandler.cpp554); this patch does not fix that engine behavior, and strict raw rejection/log checks must stay. No mechanical ACK-only acceptance is justified.
