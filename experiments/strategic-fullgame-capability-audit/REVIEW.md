# Full-game strategic capability boundary audit

This is a read-only audit of the actual WSL isolated runtime source `/root/heroes3-ai-lab/src/vcmi-adv`, not the separate Windows `vcmi` tree. Twenty source files were copied and hashed in `source-sha256.json`; `audit_evidence.py` reread current originals and copies with zero differences. No source/model/binary was edited, game launched, pool acquired, or optimizer run. All line references below refer to these preserved copies of that isolated source.

The director executes a real but narrow strategic policy. It has a scheduler capable of selecting from several owned heroes, but does not intentionally recruit a second hero, allocate multiple hero roles, deliver armies between heroes, or reserve defense. A distinct unhandled hero-exchange callback is a high-priority engineering gap before multihero courier support. It must be validated independently of the threat-release experiment.

A trained candidate selector cannot request missing recruitment/meeting/deposit operations. |

`lib/callback/CPlayerSpecificInfoCallback.cpp:47–50` returns the player's own heroes, not visible enemy heroes. It does not filter garrisoned heroes in this method. Director `pickHero` likewise does not exclude `isGarrisoned()`. A preplaced garrison hero can therefore require specific scheduling/ungarrison validation; source alone does not establish legal successful movement for it. The native API provides `swapGarrisonHero` (`CCallback.cpp:251`) and server `garrisonSwap` (`CGameHandler.cpp:2812–2857`), but Director never calls it.

The loop is not a guarantee that every usable hero moves: `issueMove` paths at `330–341` return false on unavailable path/next-turn step, and `advanceTurn:394–395` then ends the entire turn rather than marking that hero blocked and trying another. `heroMoved:419–420` also blocks a hero for the rest of the turn on same-coordinate blocking visits. The global `MAX_MOVES_PER_TURN=128` in `CDirectorAI.h:47` is shared across all heroes, not allocated per hero. These are source-derived limits requiring deliberate two-hero fixtures rather than claims that the loop is broken in existing singlehero games.

## Distinct native meeting/query mechanism

The source chain is explicit:

1. `lib/mapObjects/CGHeroInstance.cpp:579–588`: visiting a nonenemy hero calls `gameEvents.heroExchange(visiting_id,visited_id)`; this is a real native visit, not a synthetic query.
2. `server/CGameHandler.cpp:1660–1676`: constructs `CGarrisonDialogQuery`, sends **ExchangeDialog**, includes its query ID and visiting hero's player, and adds the query. This is different from **GarrisonDialog**.
3. `client/NetPacksClient.cpp:779–781`: ExchangeDialog dispatches `IGameEventsReceiver::heroExchangeStarted(hero1,hero2,queryID)`. GarrisonDialog instead dispatches `showGarrisonDialog` at `771–776`. Implementing the latter cannot answer the former.
4. `lib/callback/IGameEventsReceiver.h:105`: `heroExchangeStarted` has an empty default body. Director's inheritance is `CDirectorAI → CAdventureAI → CGlobalAI → CGameInterface`; the intermediate classes do not override this method. Thus no current Director reply/transfer is initiated for an ExchangeDialog.
5. `server/queries/MapQueries.cpp:66–75`: CGarrisonDialogQuery registers the armies' owners. It permits stack operations only on its involved IDs (`78–97`) and otherwise falls back to `CDialogQuery::blocksPack` (`139`). `CQuery.cpp:133–140` says this query ends by player answer and blocks everything except reply by default. Movement/end-turn is not a way to resolve it.
6. `lib/callback/CCallback.cpp:45–60`: `selectionMade(0,qid)` sends a real QueryReply (except invalid ID -1). `server/CGameHandler.cpp:3637–3653` checks the player's top query, verifies it can end by answer, sets reply and pops it. Zero is a valid dialog-close answer for this dialog class; it is not a troop transfer instruction.

Director query bookkeeping itself (`requestSent:461–462`, `queryResolved:469–473`, `requestRealized:435–441`) only works for callbacks that insert the pending query and actually send QueryReply. A no-op meeting callback does neither. Later moves may be rejected by the server query gate or scheduling may stop behind movement/query processing. Which symptom occurs must be recorded by the first genuine native meeting test, not guessed as an already reproduced timeout.

## Army transfer and defense constraints

Native stack operations exist and should be reused, not emulated. `CCallback.cpp:415–420` merges same-creature stacks or swaps others. Server `arrangeStacks` verifies army existence, legal slot IDs, exchange eligibility, removable garrison rules, and ownership (`CGameHandler.cpp:2181–2265`). `isAllowedExchange:3711–3720` recognizes an active matching garrison query; `3730–3740` permits town and its visiting/garrison hero; `3754–3756` recognizes two heroes sharing a town. This does **not** authorize arbitrary distant hero-to-hero transfer.

`lib/mapObjects/CGTownInstance.cpp:874–878` defines `getUpperArmy()` as the garrisoned hero when present, otherwise town army. Thus current automatic town pickup can draw from a garrison hero, not just a hero-free town. `CGHeroInstance.cpp:574–576` says heroes need their last stack; a courier/defense allocator must explicitly preserve a legal residual stack and confirm native acceptance. The current town transfer policy contains no garrison reserve or incoming-threat budget, and its per-creature transfer-attempt cache (`567–571`) is set before success, so retries/partial pickup need separate testing.

Economy is run before every movement decision (`advanceTurn:392–394`), iterates towns in callback order, spends on the first allowed priority, and then recruits as much as current resources allow. A threatened castle does not gain a budget exception. Transfer flow pulls armies into visiting heroes; there is no mirror deposit when defense needs them. Native battle defense can occur through town/hero armies and BattleAI, but choosing to remain, reinforce, or garrison a defender is not implemented as a strategic action.

## Minimum next-stage genuine mechanism tests (not executed)

Use a separate engineering version and new frozen maps/seeds, with no PPO update and no threat-release change. Keep current baseline and raw failures; serialize pool use only after parent release.

1. **Two independent mobile heroes.** One small map with two owned nongarrison heroes and separate reachable visible resource objectives, enough remaining movement to require both. Under unchanged scheduler, collect per-hero native move replies and ACKs across two turns. Require both heroes to execute useful legal movement, not merely appear in snapshots. Add one no-target/blocked hero case and one preplaced garrison-hero case to expose scheduler starvation/illegal movement without masking a failure.
2. **Real meeting and close only.** Create a two-owned-hero fixture with legal path to the other hero's distinct visitable tile. A minimal isolated mechanism harness issues native `moveHero` to that actual target after verifying the real path; it must not append a fabricated policy candidate or use a current-position move. Capture native hero visit → ExchangeDialog → real `heroExchangeStarted` with matching IDs/query ID. First retain the old version's result as control. In a separately frozen callback-only fix, send close QueryReply, observe successful PackageApplied plus QueryResolved, then execute another legal move and EndTurn. Require zero outstanding/unanswered queries and zero server rejection; keep all timeouts as engineering failures. This certifies closing the query, not courier supply.
3. **Meeting and one conservative transfer.** In a new isolated version, use that actual active query, transfer a known legal stack from courier to main hero with `ArrangeStacks`/merge callback, wait for its ACK, then close the query and wait for close ACK/resolution before moving. Keep at least one legal unit/stack on each hero. Snapshot every `(hero,creature,count)` before/after: aggregate creature counts must be conserved, recipient gain must equal donor loss, no ownership/resource/time changes may be silently invented. Test matching merge, empty-slot placement, full target, and last-stack rejection independently. A deliberately rejected operation must remain a recorded failed case and must not deadlock the close path.
4. **Small town pickup/delivery/defense fixture.** After the above pass, separately test town pickup with/without garrison hero, then a courier pickup→native rendezvous→delivery cycle and an explicit reserve/deposit action. Assert troop conservation, visit/recruit/move/transfer/query ACK sequence, legal remaining courier army, chosen garrison floor, and next-turn progress. Only then compare economy/courier/defense strategies under paired seeds; mechanism correctness alone is not a strategic benefit.

Start with the callback-close test because it is an independent engineering prerequisite for friendly rendezvous. Keep that acceptance version separate from `threatreleaseA` so subsequent strength comparisons retain a clear causal change. The current frozen source remains unchanged by this audit.

## Reproducible evidence

`AUDIT.json` contains all 32 archived native run directories, maximum simultaneous owned hero counts, distinct decision hero IDs, and event counts. `audit_evidence.py` rechecks these raw files and all source snapshots with standard Python only. Distinct hero IDs over a game are intentionally not treated as simultaneous multihero evidence. The archived native client traces/requests remain in their original WSL worker directories. Re-running this audit later after an intentional source upgrade may correctly report a live-source hash difference; the preserved source copies and original manifest remain the evidence for this review.
