# Two-hero scheduling and transport: source review only

This is a research specification, not implemented transport, native execution evidence, a learned scheduler or an expert course. No source was changed and no native/GPU operation was performed. The actual engine reviewed is `/root/heroes3-ai-lab/src/vcmi-adv`; the workspace `vcmi` tree is different. Director line references below refer to the preserved `strategic-threat-replan-v2/candidate/AI/DirectorAI/CDirectorAI.cpp`.

## Current capabilities and missing behavior

- Director88–103 picks the unblocked owned hero with greatest remaining movement. It lacks an explicit ID tie-break and does not exclude garrisoned heroes. Director332 and732–741 reject multiple heroes, including a hardcoded `own_hero_count:1` in requests; both execution and protocol must migrate together.
- Director552–563 hires only when the owned-hero roster is empty. This proves replacement hiring, not proactive second-hero recruitment.
- Director597–612 already supplies a visiting own hero from a town's actual army through native `mergeOrSwapStacks`. Its `(town, creature)` per-turn deduplication may prevent a second same-turn delivery of that creature, so a transport implementation must specify and verify new transaction progress/bounds.
- Director451 treats a zero-displacement visit as blocking that hero for the turn. A completed friendly meeting may need a different, explicit post-query eligibility rule if the courier should continue moving.
- Director830–834 closes `showGarrisonDialog`, but friendly hero meeting uses a different callback. Actual `client/NetPacksClient.cpp779–781` routes `ExchangeDialog` to `heroExchangeStarted`; current typed Director inherits the empty implementation from `lib/callback/IGameEventsReceiver.h105`.
- Actual `CPlayerSpecificInfoCallback.cpp47–50` returns the player's own hero roster. Full own-state observations are available without inspecting hidden enemy objects. The schema must distinguish owned count, movable nongarrison count and currently eligible scheduler actors.
- Actual `CGHeroInstance.cpp579–588` turns a friendly hero visit into `heroExchange`. `CGameHandler.cpp1660–1676` creates a real `CGarrisonDialogQuery` and dispatches `ExchangeDialog`. `MapQueries.cpp78–85` permits ArrangeStacks concerning only the associated armies. `CGameHandler.cpp3706–3720` accepts the query-linked exchange. This is not permission to transfer remotely between arbitrary heroes.
- Actual `CCallback.cpp415–420` selects merge versus swap according to the involved creatures. A one-way delivery must check that the recipient slot is matching or empty; an arbitrary swap is not a certified delivery.

The independent mechanism evidence in `multihero-mechanism-probe-v1-independent-audit/native-complete-assets-02/AUDIT.json` establishes real two-step meeting, compatible whole-stack transfer, query close and EndTurn. The courier's 10 Pikemen are added to the receiver's 5, while the courier retains 3 Archers. Counts are conserved and resources/positions do not change during the exchange. It does not prove general transport, second-hero hiring or a full game. Old README and prepared/source `probeResolved` gates are historical: the qualified raw proof uses actual server query pop, exact QueryReply ACK and subsequent EndTurn, not an exchange QueryResolved callback that this native query does not emit.

## Executable first scope

1. Exactly two owned land heroes, initially with compatible whole-stack transfer opportunities. Validate existing fixture mechanics first, then a separate real second-hero hiring case. Roles are a documented deterministic script, not a learned capability.
2. Deterministic fair actor rotation, with hero-specific goal, blocked reason and movement budget. At most one outstanding strategy action for the player. An exhausted/unreachable hero yields the internal scheduler to the other; this is not a native EndTurn or PPO transition.
3. Persistent transport job: return to an own town, acquire real available troops, follow the main hero by object ID, perform a real meeting/delivery, close the real query, return for another supply cycle. A moving receiver updates a bound object target, not an unrelated new map goal; death or role replacement explicitly cancels/rebinds the job. This requires extending the present `(destination, kind)` commit representation with target identity.
4. Separate query lifecycle: `open -> transfer sent/ACK -> close sent/ACK -> drained`. Original MoveHero ACK, transfer ACK and query-close events may interleave, so store distinct immutable request identities. Director-only pre-dispatch registration is preserved. Normal movement/economy scheduling resumes only once every relevant barrier is drained. No matching recipient slot means close and report incomplete delivery, never fabricate success.
5. Conservative compatible whole-stack delivery only, preserving donor/recipient armies. Seven-slot crowding, last-stack splitting, allied-player exchange, naval/cross-level routing and optimal army composition remain explicit unverified extensions.
6. True player EndTurn only after all scheduler actors finish or a separately specified player-wide decision. No hero-specific EndTurn, same-tile fake move or synthetic ACK. Per-hero caps should not silently end the other hero's usable turn; retain an overall bounded scheduler and record why it stops.

## Schema5 and recovery requirements

Requests must contain actual `own_hero_count` and explicit own roster: stable IDs, visitable positions, movement, garrison status, exact creature slots/counts, role/job and blocked status. Each per-actor request/action binds the same actual actor ID. Friendly-meeting candidates need their own kind plus `target_hero_id`; arbitrary meeting tiles cannot masquerade as frontier. Player EndTurn keeps explicit player-wide scope.

In this first scope, actor scheduling, hiring, town supply, meeting transfers and QueryReply are scripted/automatic, all recorded with actual request IDs, native application, exact ACK and state changes, and excluded from learned samples. Future learned actor choice can select hero-bound native moves in a joint candidate pool; future learned transfer requires an explicit exchange-phase action protocol. Neither should be claimed from deterministic first-scope mechanics.

Create a new encoder/model/checkpoint epoch. Preserve older immutable schema4 tools. Explicitly initialize from old weights; do not resume old Adam, rollout or checkpoint metadata under changed semantics. Single-hero compatibility fixtures can verify numerical preservation where the action/input definition is identical, but real multihero input is a new distribution. Do not hardcode count1 or label a local scheduler switch as a server-applied policy action.

Boundary recovery must bind the native save SHA to control state: role IDs, transport phase/target, actor order, own-turn identity and relevant budgets. The current save does not demonstrate that newly added C++ role/job members are serialized automatically. `CCallback.cpp313–319` exposes a native SaveLocalState request, but its use for AI control-state restoration needs its own implementation/ACK/load proof. An explicit atomically saved control sidecar bound to the native save is another research option. Save only at a defined boundary with no pending movement/query/battle/request; never discard a live transport transaction to manufacture a boundary.

## First acceptance evidence

Require both heroes to issue genuine successful moves, at least two own turns of sustained job state, exact donor-loss/recipient-gain conservation, query closure, continued legal scheduling after delivery, and fresh-process boundary restoration. Include no-compatible-slot and missing/dead receiver cases. Then run normal complete games and a separate paired supply-benefit comparison. Mechanics success alone is not a learned scheduler, economic improvement, overall strategy success or an expert demonstration.
